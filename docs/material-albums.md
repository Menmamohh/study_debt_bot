# Загрузка методичек альбомом

После выбора работы бот сразу принимает методичку. Одно фото, один документ,
каждый Telegram-альбом и отдельная текстовая методичка создают отдельные заявки.
Следующий файл можно отправить к той же работе до выхода из экрана загрузки.
Выбор типа материала больше не требуется. Старые кнопки и состояния добавления
решений сообщают, что действие недоступно. Старые решения остаются доступны для просмотра.

Фотографии одного альбома собираются по `(chat_id, user_id, media_group_id)`.
Порядок определяется по `message_id`, подпись ищется среди всех фото, все подписи
сохраняются у соответствующих вложений. Администратору приходит один альбом
и одна общая карточка. Одно решение меняет статус всей методички.
В очереди модерации есть «Открыть», показывающее все файлы заявки.

## Миграция и установка

Перед обновлением BotHost остановить бот и сделать резервную копию его SQLite-базы
через SQLite backup API либо скопировать закрытую базу вместе с необходимыми WAL-файлами.
Не копировать только основной `.db` при работающем боте с активным WAL.
Хранить резервную копию отдельно, не публиковать её в GitHub.

Обычный запуск `init_db()` добавляет три таблицы через `CREATE TABLE IF NOT EXISTS`:

- `material_attachments`: файлы методички, их порядок и подписи;
- `material_upload_events`: уникальный ключ источника и ссылка на материал;
- `material_moderation_messages`: сообщения альбома/карточки и тип показа.

Существующие таблицы не перестраиваются, строки и идентификаторы материалов
не меняются. Старые материалы читаются из прежних полей без переноса файлов.
Повторный запуск миграции безопасен. Запись материала, вложений и ключа загрузки
происходит в одной транзакции. Повторное событие не создаёт новую заявку, в том
числе после перезапуска процесса. Решение модератора применяется только один раз.

Откат к прежнему коду не требует удаления новых таблиц. Но прежний код покажет
только первый файл новых альбомов: для полного просмотра нужна эта версия.
Не восстанавливать старую базу поверх новых заявок без отдельного решения о данных.

## Уборка сообщений

Предпросмотр из очереди и просмотр студентом используют общий учёт временных
сообщений. Карточка и все фото убираются после успешного перехода на новый экран.
Успешно отправленные фотографии учитываются даже при последующей ошибке отправки карточки.
Исходные уведомления о необработанных заявках защищены от уборки.
После решения их фото и карточка становятся временными сообщениями для уборки
на следующем переходе. Заявка и файлы в базе сохраняются.

При ошибке уведомления заявка остаётся в очереди: её можно открыть оттуда.
Автоматической повторной отправки уведомления нет, чтобы не плодить дубликаты.

## Проверки и ограничения

`tests/test_material_albums.py` использует временную SQLite, настоящий FSM,
диспетчер aiogram и подменённый транспорт Telegram, который не делает сетевых
запросов. Проверяются порядок/подписи, разделение загрузок и пользователей,
дубли, модерация, совместимость, миграция, отказ отправки и уборка экранов.
Также сохраняются проверки `test_material_message_cleanup.py`,
`test_study_navigation.py` и `test_ui_lifecycle.py`.

Telegram не присылает отдельный признак завершения альбома. Сборщик ждёт секунду
без новых фотографий. Загрузка до завершения сбора и незавершённый выбор
предмета хранятся в памяти процесса: при перезапуске их надо повторить.
Сохранённые заявки, вложения, ключи дублей и номера сообщений хранятся в SQLite.
Фото, пришедшие с необычно большой задержкой после завершения сбора, не могут
быть гарантированно включены в уже сохранённый альбом.

Если Telegram принял отправку, но соединение оборвалось до получения номеров
сообщений, эти неизвестные номера невозможно зарегистрировать для уборки.
Номера старых сообщений, которые прежняя версия не сохраняла, также неизвестны.

Автотесты не подтверждают установку на BotHost и работу реального Telegram.
Эти проверки выполняет пользователь после самостоятельного обновления.
